# IA (Groq API)

A IA **explica e classifica**; não calcula. Toda soma, limite, comparação e
detecção vive em código determinístico e testado (`insight`, `budget`,
`statement`). O modelo recebe números já prontos e escreve sobre eles.

Recurso **desligável**: sem `GROQ_API_KEY` ou com a opção desligada em
Configurações, o app funciona inteiro (categorização cai para regras).

Groq (`groq.com`) hospeda modelos abertos (Llama) numa API compatível com o
formato OpenAI (`/openai/v1/chat/completions`) — tem camada gratuita, boa o
bastante para categorização em lote e narrativa de números já prontos. Troca
de provedor é só o `GroqClient`; o resto (mapper, service, cache, orçamento
de tokens) é igual, independente de quem responde.

## Três usos

### 1. Sugestão de categoria (e de pessoa)

- Entrada: `merchant`/`description` normalizados, valor, dia, conta, e a
  lista de categorias do User. **Sem** número de conta, documento, saldo,
  nem histórico completo.
- Saída: JSON estrito `{ categoryId, confidence }` validado por schema Zod;
  categoria inexistente ou formato inválido = descartado.
- Aplicação: só entra como `categorySuggested`; vira efetiva apenas acima do
  limiar de confiança **ou** com aceite do User (03). Nunca sobrescreve
  classificação confirmada.
- Lote: várias transações por chamada para reduzir custo; cache por
  `merchant` normalizado (o mesmo estabelecimento não é reclassificado).

### 2. Resumo mensal e "onde economizar"

- O servidor monta um **pacote de fatos** (JSON) a partir dos relatórios
  determinísticos: totais por categoria, variações, assinaturas detectadas,
  anomalias, ritmo do orçamento. O modelo escreve o texto **usando só esses
  fatos**; o prompt proíbe inventar número.
- Cada sugestão da tela traz o cálculo de origem (link para o relatório),
  para o User conferir. Resumo é cacheado por `(userId, mês, hash dos
fatos)`: só regenera se algo mudou.

### 3. Chat sobre os próprios dados

- Implementado com **tool use somente-leitura**. O modelo não escreve SQL e
  não tem acesso ao banco; ele chama ferramentas fixas, por exemplo
  `spending_by_category(month)`, `top_merchants(month, limit)`,
  `compare_months(a, b)`, `list_subscriptions()`, `statement(accountId, month)`.
- **`userId` nunca é parâmetro de ferramenta**: é injetado pelo servidor a
  partir da sessão. O modelo não consegue pedir dado de outro User.
- Ferramentas devolvem só agregados/linhas mínimas, com **limite de linhas**.
- **Nenhuma ferramenta com efeito colateral** (não classifica, não apaga, não
  conecta banco). O modelo pode _sugerir_ uma ação; quem executa é o User na
  interface, com confirmação.
- Limite de rodadas de ferramenta por pergunta (ex.: 5) e de tamanho de
  resposta.

## Privacidade e minimização

- Enviar o mínimo: descrição do estabelecimento, valor, data, categoria,
  rótulo de pessoa. **Nunca**: número de conta/cartão, CPF/CNPJ, tokens,
  e-mail, senha, saldos que a pergunta não precise.
- **Só compra no cartão vai para a IA.** Pix e movimentações de conta (que
  trazem nome de terceiros) **nunca** são enviados, nem pelas ferramentas do
  chat: nenhuma ferramenta lê `Movement`.
- **Nome de familiar** é dado de terceiro: por padrão vai como rótulo
  pseudonimizado (`Pessoa A`) e o servidor troca de volta na resposta.
  Configurável.
- Confirmar e registrar nos docs, antes de ligar em produção, as condições de
  retenção/uso de dados da API contratada — não assumir.
- Chamada só do servidor; a chave nunca vai ao browser.

## Segurança contra injeção via dado

Descrição de transação é **texto controlado por terceiros** (o estabelecimento
escolhe o que aparece). Trate como não-confiável:

- Dado do banco entra no prompt **delimitado e rotulado como dado**, nunca
  misturado com instruções; o system prompt diz explicitamente para ignorar
  instruções contidas em descrições.
- Como as ferramentas são somente-leitura e escopadas ao User, o pior caso de
  uma injeção é uma resposta ruim — não vazamento nem ação.
- Saída do modelo é renderizada como **texto** (ou markdown sanitizado, sem
  HTML, sem imagens/links remotos automáticos) — nunca `dangerouslySetInnerHTML`.
- Saída estruturada é sempre revalidada por schema; ID vindo do modelo é
  conferido contra o que pertence ao User antes de usar.

## Custo e limites

- `AI_MONTHLY_TOKEN_BUDGET` por User: ao estourar, o recurso pausa com
  mensagem clara até virar o mês (categorização por regras continua).
- Rate limit por User nas rotas de IA (mais estrito que as de leitura).
- Timeout explícito em toda chamada; falha da IA **nunca** quebra uma tela
  ou um sync — degrada para "sem sugestão".
- Modelo por env (`AI_MODEL`), com modelo menor/mais barato para
  categorização em lote e um mais capaz para resumo/chat, se fizer sentido
  na prática. Registrar tokens usados por chamada (sem conteúdo) para
  acompanhar custo.

## Testes

- `GroqClient` sempre mockado. Testes cobrem: resposta com JSON inválido,
  categoria inexistente, confiança abaixo do limiar, estouro de orçamento de
  tokens, tentativa de tool call com `userId` no argumento (ignorado),
  descrição com texto tipo "ignore as instruções anteriores" (tratada como
  dado).
- Avaliação de qualidade da categorização (acurácia num conjunto real
  anonimizado do próprio dono) antes de aumentar a autonomia da IA.
